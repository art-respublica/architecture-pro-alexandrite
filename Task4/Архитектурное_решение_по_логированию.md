#### Анализ компании в контексте планирования логирования

В компании нет системы логирования событий внутри backend сервисов.
Из-за непонятно в каком именно системе произошел сбой при обработке входящего запроса.
Входящие запросы поступают с фронта онлайн-магазина и по API в MES систему.

Планируется добавить логирования ключевых событий для back-end сервисов для анализа сквозного выполнения запроса.
Обязательно нужно логировать: входящие и исходящие запросы, показатели расчета, ключевые переходы внутри сервисов.
Также нужно логировать ошибки валидации, ошибки при обработке запросов, ошибки среды: timeout, недоступность сервисов и т.п.
Каждое событие должно включать в себя идентификатор заказа, идентификатор сервиса, дату исполнения.
Логирование предлагается добавить для Shop API, CRM API, MES API.
Так как заказ может зависнуть или сломаться на любом этапе обработки в этих сервисах или их интеграции с брокером сообщений или записи / чтения из БД.


#### Мотивация
Что даст компании логирование событий в сервисах?
Внедрение логирования в связке «онлайн-магазин → CRM → MES» так же критично, как и мониторинг. 
Если мониторинг отвечает на вопрос «что случилось?» (метрики, алерты), то логирование отвечает на вопрос «почему это случилось?» (контекст, причины, цепочка событий).

1. Без логов невозможно расследовать инциденты
2. Логирование предоставляет дополнительная информации изнутри сервисов в дополнение к сквозное отслеживанию запросов между сервисами (трассировке).
3. Логи - это доказательная база для SLA и произошедших событий.
4. Логирование как и трейсинг способствует пониманию связей между сервисами компании, прозрачному отслеживания запросов между ними.
5. С помощью логирования намного легче проводить обучение новых разработчиков по сервисам компании.
6. Логи помогают тех.поддержке расследовать инциденты самостоятельно, без привлечения разработчиков.

Логирование может повлиять на изменение следующих метрик в лучшую сторону:
1. Среднее время восстановления системы после сбоя (Mean Time To Recovery).
2. Среднее время обнаружения инцидента (Mean Time to Detect)
3. Доля успешных расследований инцидентов.
4. Частота повторных инцидентов, так как по логам "можно докопаться" до причины ошибки или сбоя.
5. Уровень интеграционной надежности.
6. Процент нахождения потерянных заказов. 
7. Время обработки инцидента поддержкой.
8. Финансовые потери от сбоев и ошибок.

#### Предлагаемое решение
В spring boot приложения будет добавлен фреймвормк zalando для записи логов. Будут разработан определенный шаблон сообщения лога в формате json.
В сообщении будут обязательные поля: timestamp, level, service, message, orderId, error, duration, spanId, traceId.
Необязательные поля: clientId, partnerId.
В MES API (С#) будет реализована аналогичная функциональность с помощью Serilog.

Также предлагается развернуть несколько контейнеров OpenSearch стека.
Логи в контейнерах будут записываться в файлы, которые будут вычитываться с помощью сборщика FluentId, обогащаться и сохраняться в хранилище OpenSearch. 
На уровне записи логов в файл должны быть настроены шаблоны, которые будут вырезать из логов чувствительные данные (пароли, номера карт, токены) до того, как они попадут в хранилище.
С помощью OpenSearch UI пользователи смогут получить логи в удобном для себя виде.
Логи будут храниться не больше 30 дней. Индексы будут ротироваться для каждого сервиса отдельно.


#### Мероприятия по анализу логов.
Поддержка приложений в лице продакт-менеджера и дежурные разработчики должны каждый день анализировать логи на предмет залогированных ошибок.
При разборе индцидентов обязательно прикладывать traceId для быстрого нахождения логов.
Логи не должны использоваться для предотвращения DDOS-атак или подсчета бизнес-показателей, для решения подобных задач настроен мониторинг.
