#### Существующие и потенциальные проблемы текущего архитектурного решения (AS IS)

###### Бизнес-функциональность.
1. Текущая архитектура не подразумевает единой системы по отслеживанию статуса заказа клиента. 
   Фактически у компании нет master системы.
   Это приводит к проблеме "у семи нянек дитя без глазу", то есть отсутствию ответственного за заказ со стороны компании. 
   Ни пользователь, ни продавцы не могу своевременно понять, что с заказами есть проблемы. 
   Начальная часть жизненного цикла заказа проходит в системе онлайн-магазина и может отслеживаться в CRM системе из-за используемой единой базы данных для этих систем.
   Потом заказ передается в MES систему. Продавцы не имеют доступ в эту систему. Операторы выбирают заказы исходя из вознаграждения.
   То есть потенциально допускается существование массива заказов, которые долго не берутся в работу из-за невыгодности.
   Закрытие заказа происходит вручную после получения сообщения от транспортной компании о доставке или по истечении времени.
2. Множество ручных операций по работе с заказами увеличивают трудозатраты менеджером и продавцов, что является ограничителем для масштабирования бизнеса.   
3. ИТ-система компании в целом не является наблюдаемой. 
   В системе нет единой системы логирования происходящих событий. 
   Нет единой системы трассировки запросов внешнего и межсистемного взаимодействия.
   Нет единой системы мониторинга метрик в ежедневном режиме.
   Все это приводит к реактивному поведению продавцов и операторов, которые реагируют на проблемы, сообщаемые клиентам.
4. Нет единой базы данных компании, они распределены по двум базам данным: Shop DB, MES DB. 
   Это означает, что агрегация данных для различной видов отчетности происходит вручную, а не автоматически.
5. Нет автоматической интеграции с внешними системами, например системой по отслеживанию груза транспортной компании.
   Отслеживание грузов происходит не в автоматическом режиме.
6. Заказы от других продавцов ювелирных изделий идут напрямую в MES систему. 
   Что создает для операторов конкурентную гонку между заказами от "своих" и сторонних продавцов.
7. Компания не рассчитывает выгодность каждого заказа и не расставляет приоритеты между заказами от различных продавцов.


###### Разработка in-house решений.
1. Релизный цикл компании - это двухнедельный спринт компании. 
   За время спринта могут разрабатываться несколько эпиков и сторей. 
   Они могут влиять друг на друга, что увеличивает тестирование каждой задачи и время на регрессионное тестирование.  
   То есть увеличивает время time-to-market новой функциональности.
2. В компании нет автоматических тестов для регрессионного тестирования. 
   Это приводит к большой нагрузке на QA инженера при выпуске релиза. 
   Потенциально способствует не своевременному обнаружению ошибок. 
3. В компании разрешено пропускать в прод ошибки уровня middle и low. 
   Мелкие ошибки и недоработки не способствует росту удовлетворенности клиентов и продавцов от ИТ-систем в целом.
   Также есть риск сознательного понижения уровня ошибки для развертывания релиза.
4. В компании один QA инженер, что является bus-фактором для команды инженеров и узким горлышком в процессе выпуска релиза.
   В компании уже есть значительные задержки выпуска релизов.
5. Количество разработчиков соответствует один к одному количеству систем. Что тоже является потенциальным bus-фактором.


#### Предлагаемое архитектурное решение (TO BE), устраняющие указанные проблемы и нежелательные ситуации. 
1. Предлагается выделить единую точку отслеживания всех заказов и их жизненного цикла, то есть создать master систему.
   В качестве такого предлагается сделать CRM систему. 
   В ней необходимо фиксировать изменения всех статусов по всем заказов. То есть необходимо реализовать в смежной системе MES отправку события об изменении статуса в CRM систему.
   Также в ней необходимо фиксировать все заказы от сторонних продавцов. Фактически это такие же заказы, но с укороченным жизненным циклом.
   В ней предлагается добавить дашборды по воронке прохождения заказов по статусам, и количеству заказов, зависших дольше необходимого времени в каких-то статусах.
   Предлагается, что за эти дашборд будет отвественный.
2. Предлагается добавить в систему функциональность динамического расчета выгодности для компании каждого заказа.
   Для более выгодных заказов для компании будет увеличена выгода для операторов.
   Для невыгодных для компании заказов будет инициирована процедура отказа от заказа.
   Расчет выгодности заказа планируется производить после этапа подсчета стоимости заказа PRICE_CALCULATED перед подтверждением заказа MANUFACTURING_APPROVED.
3. Предлагается добавить мониторинг ключевых бизнес-показателей и технических показателей, логирование и трейсинг всех совершаемых действий.
4. Предлагается реализовать интеграцию со смежными компании, в первую очередь транспортной компании.
   Для автоматического отслеживания факт отправки и доставки заказа покупателю.
5. Для процесса разработки предлагается перейти на релизный цикл по одному эпику с максимальной периодичностью в неделю.
   В идеале с возможностью непрерывного развертывания по требованию.
   Для реализации этого требования необходимы автоматические тесты для тестирования уже разработанной функциональности и процесс разработки автоматических тестов для новой функциональности.
   Это нельзя достичь силами одного QA-инженера.
   Предлагается нанять в команду разработки еще одного QA инженера с компетенцией разработки автоматических тестов.
   А также повысить квалификацию уже нанятого QA инженера в разработке автотестов с помощью обучения.
6. Предлагается запретить выпускать релизы при обнаружении багов любых типов в них.
   Принять политику приоритета правки обнаруженных в проде ошибок.
7. Провести нагрузочное тестирование текущей функциональности для определения границ масштабируемости бизнес-показателей.


#### Список инициатив, расставленных в порядке приоритета.
###### Срок 1-2 кварталов
1. В первую очередь предлагается сделать CRM систему master - системой по заказам.
   Необходимо реализовать:
   - функциональность отправки событий изменения статуса из MES системы в CRM систему,
   - функциональность фиксации заказов от других продавцов в CRM-системе с укороченным жизненным циклом,
   - АРМ для продавцов с отображением воронки прохождения заказов по статусам и списка "зависших заказов".
   Выделить ответственного за своевременную обработку заказов, в задачи которого будет включен разбор "сложных" случаев.
2. Параллельно с разработкой новой функциональности в качестве второго приоритета предлагается повысить наблюдаемость ИТ-системы:
   - добавить мониторинг технических параметров функционирования системы
   - добавить мониторинг ключевых бизнес-показателей системы для менеджмента
   - добавить логирование всех событий системы, то есть всех действий, совершаемых внутри каждой ИТ-системы, и запросов межсистемного взаимодействия,
   - трейсинг всех запросов в каждой ИТ-системе.
   Без этого невозможно убрать задержки развертывания релизов, увеличить скорость разработки и вывода ее в прод, повысить масштабируемость системы.
3. Принять политику приоритета правки обнаруженных в проде ошибок и выпуска релизов без багов.
   Для этого придется выделить 1-2 спринта для исправления текущих багов.
4. Предлагается нанять нового QA инженера и начать процесс разработки автоматических тестов текущей функциональности. 
   (Без дополнительного QA будет сложно реализовать предыдущий пункт 3.) 

###### Срок 3-6 кварталов
1. На следующем этапе предлагается добавить динамический расчет выгодности каждого заказа с динамическим определением выгоды оператора для каждого заказа.
2. Реализовать интеграцию с транспортной компанией.
3. Добавить функциональность непрерывного развертывания релизов и перейти на политику "релиз по требованию".
4. Провести нагрузочное тестирование текущей функциональности. Определить потенциальные проблемы при масштабировании.
