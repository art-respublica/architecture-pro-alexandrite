#### Анализ компании в контексте планирования мониторинга

В компании нет системы сквозной системы мониторинга бизнес-показателей, показателей производительности и показателей системного уровня. 
Сайт компании подключен к Яндекс Метрике. Но так как компания предоставляем возможность оформления другим продавцам через внешнее api,
данные из Яндекс Метрики не дают полной картины по заказам. 
Планируется, что количество заказов с онлайн-магазина и по api будет относится друг к другу как 30/70.
Также нет единого дашборад для отслеживания и анализа показателей производительности и показателей системного уровня.
Разработчик каждой системы мониторит свою систему самостоятельно, иногда привлекая DevOps инженера. 

Компания планирует добавить мониторинг ключевых показателей.


#### Мотивация

Что даст компании мониторинг?
1) Наличие единой картины сквозного бизнес-процесса. Например:
    а) сквозные трекинги заказа от начального статуса INITIATED до финального статуса CLOSED
    б) позволить выявить узкие места в процессе
    в) определить среднее время выполнения заказа (lead time)
2) Позволить оценить реальную производительность ИТ-систем. Например:
    а) позволит определить время ответа на запросы по api и со стороны сайта,
    б) количество успешных / ошибочных запросов в секунду
    в) загрузку процессоров, памяти, дисков, сетевых каналов используемого оборудования,
    г) позволит спрогнозированить дневные и сезонные пики.
3) Значительно уменьшит потери заказов из-за сбоев оборудования или человеческого фактора. Например, с помощью: 
    а) автоматического оповещения при "зависании заказа в статусе" или сбоев на стороне оборудования,
    б) контроля воронки оформления заказов.
4) Наличие бизнес-показателей в реальном времени. Например:
    а) количество новых заказов в час / день
    б) конверсию заказов по воронке оформления заказов
    в) долю брака на производстве по количеству незакрытых заказов
    г) текущую загрузку производственных мощностей.
5) SLA для обработки заказов. Невозможность отслеживания запросов между системами размывает отвественность между системами и обслуживающими их специалистам.
6) Историю инцидентов с привязков к коду ошибки или системе-виновнику.
7) Возможность планировать масштабирование и расширение бизнеса.
8) Уменшит время обнаружения и устранения сбоев.
9) Значительно снизит потерю репутации и денег компании из-за скрытых проблем.
   
Итог: Без мониторинга компания слепа, глуха и нема в отношении здоровья своего бизнес-ИТ-ландшафта. 
С мониторингом — получает прозрачность, скорость реакции и данные для развития.


#### Выбор подхода к мониторингу

Для эффективного мониторинга лучше всего использовать комбинацию подходов: 
- RED (Requests Rate, Errors, Duration) для анализа запросов с онлайн-магазина или по API, 
- USE (Utilization, Saturation, Errors) для инфраструктуры (серверов, баз данных, брокеров сообщений и т.п.), 
- «Четыре золотых сигнала» (Latency, Traffic, Errors, Saturation) для общего состояния системы,
- показатели конверсию заказов для ключевых связок статусов.

Метрики предлагается собирать в сервисах с помощью фреймворка Prometheus. 
Для инфраструктуры предлагается снимать метрики баз данных, очередей сообщений.
Отображать метрики предлагается с помощью системы визуализации Grafana.


#### Отслеживаемые метрики

Онлайн-магазин:
- Requests Rate: число запросов в секунду (Number of requests (RPS) for internet shop API)
- Errors - число ошибок (Number of HTTP 500 for shop API), число успешных запросов (Number of HTTP 200 for shop API), их отношение.
- Duration - P50, P95, P99 времени ответа (Response time (latency) for shop API)
  
CRM:
- Requests Rate: число запросов в секунду (Number of requests (RPS) for CRM API)
- Errors - число ошибок (Number of HTTP 500 for CRM API), число успешных запросов (Number of HTTP 200 for CRM API), их отношение.
- Duration - P50, P95, P99 времени ответа (Response time (latency) for CRM API)
  
MES API:
- Requests Rate: число запросов в секунду (Number of requests (RPS) per user for MES API)
- Errors - число ошибок (Number of HTTP 500 for MES API), число успешных запросов (Number of HTTP 200 for MES API), их отношение.
- Duration - P50, P95, P99 времени ответа (Response time (latency) for MES API)

Инфраструктура (Shop DB, MES DB, Files Storage, Rabbit MQ:
- Utilization: Memory Utilisation for shop db instance, Memory Utilisation for MES db instance, IOPS дисков БД.
- Saturation: Number of connections for shop db instance, Number of connections for MES db instance, Number of message in flight in RabbitMQ
- Errors: Number of dead-letter-exchange letters in RabbitMQ, ошибки диска, ошибки репликации

Общее состояние системы:
- Latency - среднее время создания заказа, от создания заказа до старта расчета, время расчета, время производства по заказу 
- Traffic - общее количество запросов, количество созданных заказов
- Errors - общее количестов неуспешных пользовательских действий
- Saturation - длина очереди заказов на расчет, загрузка производственных мощностей, размер файлового хранилаща.

Показатели конверсию заказов для ключевых связок статусов
- отношение количество созданных заказов (SUBMITTED) к заведенным заказам (INITIATED)
- отношение количество расчитанных заказов (PRICE_CALCULATED) к заведенным заказам (INITIATED)
- отношение количество подтвержденных заказов (MANUFACTURING_APPROVED) к заведенным заказам (INITIATED)
- отношение количество выполненых заказов (SHIPPED) к заведенным заказам (INITIATED)
- отношение количество закрытых заказов (CLOSED) к заведенным заказам (INITIATED)


#### План действий

Реализовать следующие задачи:
1. Поднять Prometheus сервер, разделить сбор метрик для трех сред: dev, release, prod
2. Развернуть инструмент визуализации Grafana для трех сред сред.
3. Добавить в back-end онлайн-магазина поддержку фреймворка prometheus, интегрировать с Prometheus server.
4. Добавить в back-end CRM поддержку фреймворка prometheus, интегрировать с Prometheus server.
5. Добавить в back-end MES поддержку фреймворка prometheus, интегрировать с Prometheus server.
6. Интегрировать в Prometheus сервер сбор метрик с СУБД, file storage и RabbitMQ
7. Добавить дашборды показателей RED для всех систем и всех сред в grafana.
8. Реализовать сбор кастомных метрик.
9. Добавить дашборды общего состояния системы и конверсии заказов.

#### Показатели насыщенности
Загрузка производственных мощностей - при загрузке приближающейся к 100% ограничить прием новых заказов, так как они все равно не будут своевременно выполнены.
Длина очереди заказов на расчет - увеличение длины очередей заказов на расчет в 2 раза сигнализирует о росте заказов, необходимо приоритезировать заказы по выгодности перед взятием их в обработку.
Размер файлового хранилища - при приближении к 80% использованного файлового хранилища необходимо перенести файлы закрытых заказов в архив, очистить данные не обрабатываемых устаревших заказов.
