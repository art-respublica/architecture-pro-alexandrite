#### Анализ компании в контексте планирования трейсинга

В компании нет системы трейсинга запросов внутри cистемы.
Из-за непонятно в каком именно системе произошел сбой при обработке входящего запроса.
Входящие запросы поступают с фронта онлайн-магазина и по API в MES систему.

Планируется добавить трейсинг для back-end сервисов для анализа сквозного выполнения запроса.
То есть добавить его для Shop API, CRM API, MES API.
Так как заказ может зависнуть или сломаться на любом этапе обработки в этих сервисах или их интеграции с брокером сообщений или записи / чтения из БД.


#### Мотивация
Что даст компании трейсинг?
Внедрение трейсинга необходимо для:
- понимания связей между сервисами компании, прозрачного отслеживания запросов между ними, 
- мгновенного нахождения «узких мест» в процессе обработки запросов с целью оптимизации производительности, 
- понимания поведения системы при ошибках и сбоях, быстрой диагностики ошибок и сокращения времени простоя системы при сбоях,
Также косвенно трейсинг даст компании 
- снижение затрат на поддержку, 
- повышение скорости разработки,
- улучшение пользовательского опыта за счет стабильной работы приложения.

Трейсинг может повлиять на изменение следующих метрик в лучшую сторону:
1. Среднее время восстановления системы после сбоя (Mean Time To Recovery).
2. Среднее время отклика (Latency). Трейсинг позволит проанализировать 5% самых медленных запросов и оптимизировать их, что улучшить общую скорость.
3. Количество ошибок (Errors). Быстрая диагностика поведения системы при ошибках позволит исправить большее количество ошибок, что снизить общее количество обнаруживаемых на проде ошибок.
4. Конверсия заказов (Conversion Rate). Стабильная и быстрая работы системы прямо повышают конверсию заказов, так как пользователи будут меньше отваливаться на начальных этапах жизненного цикла заказа.
5. Скорость выпуска новой функциональности (Time to market). Разработчики будут тратить меньше времени на анализ ошибок и сбоев системы, что увеличить время разработки.
6. Удовлетворенность клиентов (Customer Satifaction Score / Index). Косвенно увеличивается при уменьшении технических ошибок и сбоев.


#### Предлагаемое решение

Для реализации трейсинга сегодня стандартом де-факто является OpenTelemetry (OTel). 
Это универсальный набор инструментов, который позволяет не привязываться к конкретному вендору (Jaeger, Zipkin, Grafana Tempo и др.) и легко менять хранилище данных в будущем.
Предлагается, что Open Telemetry инструментарий будет собирать метрики, а Jaeger будет хранить и отображать трейсинг запросов. 

Для Spring Boot на Java и С# есть готовые встраиваемые библиотеки OpenTelemetry и Jaeger.
Также отдельно нужно будет развернуть Open Telemetry Collector и Jaeger storage для быстрого сбора и сохранения метрик запросов.
Для визуалиции предлагается развернуть Jaeger UI сервис.
Для всех трех сервисов, в которые добавляется трейсинг, подключить бибилотеки OTel и потребуется настроить передачу окружения
Также необходимо проверить, что внутренняя сеть компании не "обрезают" заголовки трейсинга.

#### Компромиссы
1. Высокая стоимость хранения данных трейсинга.
Трейсинг генерируют огромный объем данных — значительно больше, чем логи или метрики.
При миллионах запросов в секунду хранение 100% трейсов обойдется дороже, чем работа самой системы. 
Если у компании ограничен бюджет на инфраструктуру, то лучше хранить трейсы за последние 2-4 недели.
Или использовать Sampling, то есть запись только 1% или 5% запросов, но тогда польза от трейсинга может исчезнуть.
2. Отсутствие культуры работы с данными трейсинга.
Для команды разработки нужно будет провести обучающий вебинар по использованию данных трейсинга в работе.
3. Трейсинг не раскроет информацию о обработке запроса внутри каждой системы.
Он позволит отследить передачу запроса от системы к системе и в БД или очередь сообщений.
4. Трейсинг требует проброса Trace ID через все шлюзы и балансировщики, что требует их донастройки.
5. Может потребоваться более долгая доработка проприетарной системы MES по сравнению со spring boot приложениями.


#### Аспекты информационной безопасности
1. Доступ к Jaeger UI трейсинга будет возможен только через корпоративную учетную запись (LDAP/AD). 
   Разработчики будут видеть только свои сервисы, а администраторы — всю систему.
2. Доступ к Jaeger UI из внешнего контура запрещен.
3. На OTel коллекторы будут приниматься трейсы только от перечисленных в списке систем.
4. На уровне OTel Collector должны быть настроены процессоры, которые будут вырезать из трейсов чувствительные данные (пароли, номера карт, токены) до того, как они попадут в хранилище.
5. Трафик между сервисами и коллектором будет шифроваться. 
   Это гарантирует, что злоумышленник внутри сети не сможет подделать трейсы или «прослушать» их.
6. На OTel коллекторе должны быть настроены ограничения на случай сбоев сервисов для предотвращения ddos-атак.
